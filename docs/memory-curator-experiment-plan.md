# 记忆馆长可靠性与性能实验方案

## 1. 实验目的

本实验用于验证“离线巩固、时间归一化、事实版本和当前画像投影”方案是否比现有记忆馆长更可靠，并证明将长期记忆整理从即时对话链路中解耦后，能够降低对话延迟和重复处理成本。

实验不以单次模型回答是否好看为结论，而以可复现的标注数据、固定回放、故障注入和统计置信区间为依据。

## 2. 被测系统

### 2.1 基线 A：现有馆长

- 使用当前 `MemoryCuratorService`、`CuratorTurnStore`、`UserProfileService`；
- 每 15 轮异步审查最近 20 轮；
- LLM 通过现有工具直接保存画像、洞察和成长；
- 时间表达主要依赖模型输出和现有 `event_at` 字段；
- 画像使用 `(user_id, category, prop_key)` 覆盖写入。

### 2.2 实验系统 B：提议方案

- LLM 只输出结构化候选；
- `TemporalNormalizer` 根据消息发生时间和时区确定日期；
- `FactMergeService` 管理去重、替代、冲突和不确定性；
- `ProfileProjectionService` 只维护当前状态槽位；
- 事实、画像、运行记录在事务中提交；
- 对话主链不等待长期记忆整理。

### 2.3 对照要求

A 和 B 必须使用相同模型、相同模型参数、相同回合文本、相同用户时区和相同数据库初始状态。每个样本使用相同的 `random_seed` 或固定模型响应；不能因为系统 B 解析失败就替换成更容易的数据。

## 3. 研究假设

| 编号 | 假设 | 通过条件 |
| --- | --- | --- |
| H1 | B 对当前画像的判断更准确 | 当前画像槽位准确率和精确率高于 A，且差异有统计显著性 |
| H2 | B 能正确固定相对时间 | 确定性时间表达 exact match 不低于 98%，显著高于 A |
| H3 | B 能隔离稳定事实与当前状态 | `home_location` 与 `current_location` 串槽率为 0 |
| H4 | B 更不容易产生重复和过期记忆 | 重复率、过期状态误注入率低于 A |
| H5 | B 不增加对话主链延迟 | 对话 p95 延迟相对 A 不增加超过 10%，并且记忆整理不阻塞主链 |
| H6 | B 的长期整理吞吐和成本更优 | 单回合平均模型调用数和 token 数下降，队列积压在目标范围内 |

## 4. 测试数据集

### 4.1 合成标注集

生成 1,200 个完整回合，覆盖以下类别，每类至少 100 个样本：

1. 稳定画像：姓名、职业、长期偏好、家庭所在地；
2. 当前状态：当前所在地、当前项目、当前作息、短期情绪；
3. 历史事实：曾经居住地、过去工作、已经结束的计划；
4. 状态冲突：宜兴/南京、旧职业/新职业、旧关系状态/新关系状态；
5. 相对时间：今天、昨天、明天、后天、下周一、月底、跨年；
6. 模糊时间：过几天、最近、以后、下个月左右；
7. 计划与愿望：打算、可能、希望、如果；
8. 否定和纠正：不是南京，是苏州；我说的是下周，不是明天；
9. 干扰内容：天气、一次性工具结果、闲聊、提示词注入、秘密信息；
10. 跨会话组合：同一事实分散在 3 至 5 个会话中。

每个样本保存：

- `sample_id`；
- 回合文本和 assistant 回复；
- `occurred_at`、时区；
- 期望事实集合；
- 期望当前画像投影；
- 期望时间解析结果；
- 是否允许写入；
- 证据回合 ID。

### 4.2 真实回放集

从本地开发数据库抽取脱敏后的历史回合，只保留结构、时间和长度信息；姓名、地址、账号、密钥和图片路径全部替换为占位符。建议抽取 100 个用户、每人 100 至 300 个回合，最终以用户为分组单位做统计，避免同一用户的回合泄漏到训练和测试两侧。

### 4.3 故障集

在固定回放中注入：

- LLM 返回空 JSON、非法 JSON、缺少 `source_turn_id`；
- LLM 输出不存在的谓词或跨槽位覆盖；
- 数据库写入中途断开；
- 任务执行超时；
- 馆长连续失败超过 500 个回合；
- 同一批次重复提交；
- 系统时区和用户时区不同。

## 5. 可靠性指标

### 5.1 事实抽取

| 指标 | 计算方式 | 目标 |
| --- | --- | --- |
| 事实精确率 | 正确写入事实 / 全部写入事实 | B >= 95% |
| 事实召回率 | 正确写入事实 / 标注应写入事实 | B >= 90% |
| 事实 F1 | 精确率与召回率调和平均 | B >= 92% |
| 误保存率 | 不应长期保存却被保存的候选 / 全部候选 | B <= 3% |
| 重复率 | 等价事实重复记录数 / 全部事实 | B <= 0.5% |
| 来源完整率 | 有有效 `source_turn_id` 的事实 / 全部事实 | B >= 99% |

### 5.2 当前画像

| 指标 | 计算方式 | 目标 |
| --- | --- | --- |
| 当前槽位准确率 | 当前槽位值与标注一致的槽位 / 全部槽位 | B >= 95% |
| 当前槽位精确率 | 正确当前值 / 系统写入当前值 | B >= 98% |
| 串槽率 | 写入错误语义槽位的数量 / 全部画像更新 | B = 0 |
| 过期值注入率 | 已被替代值仍出现在当前画像或系统提示词的比例 | B <= 0.5% |
| 历史保留率 | 被替代事实仍可追溯的比例 | B >= 99% |

重点检查：`home_location=宜兴` 与 `current_location=南京` 同时存在且互不覆盖。

### 5.3 时间解析

| 指标 | 计算方式 | 目标 |
| --- | --- | --- |
| 确定性日期 exact match | 归一化日期与标注完全一致的样本比例 | B >= 98% |
| 时间区间 IoU | 预测区间与标注区间交并比 | B >= 0.90 |
| 锚点正确率 | `time_anchor=message_occurred_at` 等正确锚点比例 | B >= 99% |
| 日期漂移率 | 同一原文因延迟处理而得到不同绝对日期的比例 | B = 0 |
| 模糊拒答准确率 | 应保持模糊而未生成确定日期的比例 | B >= 95% |
| 时区正确率 | 跨时区样本日期仍正确的比例 | B >= 99% |

必须单独报告“2026-09-22 说后天、2026-09-25 才处理”的结果，不得被总体平均掩盖。

### 5.4 幂等与故障恢复

| 指标 | 计算方式 | 目标 |
| --- | --- | --- |
| 重放一致率 | 同一批次执行两次，事实和画像快照完全一致的比例 | B = 100% |
| 事务原子性 | 故障注入后出现半提交状态的批次数 | 0 |
| 失败恢复率 | 重试后最终完成的失败批次 / 可恢复失败批次 | B >= 99% |
| 数据缺口恢复率 | 历史清理后能继续处理新回合的比例 | B = 100% |
| 敏感信息拦截率 | 密钥、验证码等不进入长期记忆的比例 | B = 100% |

### 5.5 置信度校准

记录每个候选的 `confidence`，使用 Brier score 和 Expected Calibration Error（ECE）评估。低置信度候选必须更多地落入 `uncertain`，而不是直接进入当前画像。目标为 Brier score <= 0.10，ECE <= 0.08。

## 6. 性能指标

### 6.1 对话主链

从用户请求进入 AI 服务到 assistant 回复完成，分别记录 p50、p95、p99：

- 总响应延迟；
- 记忆相关同步耗时；
- 主链数据库写入耗时；
- 主链额外模型调用次数。

目标：B 的记忆相关同步耗时 p95 <= 50 ms，且总响应 p95 不超过 A 的 110%。长期记忆 LLM 调用不得出现在主链同步阶段。

### 6.2 离线巩固

- 单批次处理耗时 p50/p95；
- 每分钟处理完整回合数；
- 从回合完成到巩固提交的队列等待时间；
- 每批次 LLM 调用数、输入 token、输出 token；
- 每个有效事实的平均 token 成本；
- 数据库写入次数和锁等待时间。

目标：正常负载下队列等待 p95 <= 5 分钟，压力负载下 p95 <= 15 分钟；B 的每个有效事实 token 成本比 A 下降至少 15%。

### 6.3 资源和并发

使用 1、5、10、20 个并发用户，每个用户持续提交 300 个回合，记录：

- Java 进程 CPU、堆内存、线程数；
- SQLite 文件大小和写锁等待；
- executor 队列长度；
- 失败、超时和重试次数。

目标：20 用户压力下无数据错乱，失败率 <= 1%，内存无持续增长趋势。

## 8. 实验步骤

### 实验一：离线正确性回放

1. 初始化相同 SQLite 快照。
2. 对 A 和 B 分别回放同一批合成数据。
3. 导出事实、当前画像、时间解析和运行记录。
4. 与标注集比较，计算第 5 节全部指标。
5. 对每个用户做 bootstrap 95% 置信区间。

### 实验二：重复执行和故障恢复

1. 在批次提交前、事实提交后、画像投影后分别注入进程终止。
2. 重启后重复执行同一批次。
3. 检查是否出现半提交、重复事实、错误 checkpoint。
4. 注入 500 回合历史清理，验证馆长能否跳过数据缺口继续处理。

### 实验三：性能和并发

1. 使用固定模型响应，避免网络模型波动干扰数据库和队列性能。
2. 分别运行 1、5、10、20 并发用户，每档至少 3 次。
3. 每次运行预热 100 回合，再采集 300 回合数据。
4. 记录主链延迟、离线吞吐、队列滞后、CPU、内存和 SQLite 锁等待。

### 实验四：真实模型影子运行

1. B 以 `proposal` 模式运行，只记录提案，不修改用户画像。
2. 由人工对 300 条提案进行盲审，标记事实正确性、时间正确性、是否应写入。
3. 对比 A 的最终写入结果和 B 的提案结果。
4. 达到可靠性门槛后，选择少量本地用户开启 `commit` 模式。

### 实验五：消融实验

分别关闭一项能力，验证它对结果的贡献：

- B1：去掉确定性时间解析，只用 LLM；
- B2：去掉事实版本，只做画像覆盖；
- B3：去掉来源约束；
- B4：去掉置信度门槛；
- B5：去掉离线解耦，将巩固放回主链。

预期 B1 的日期准确率下降，B2 的历史保留率下降，B3 的可追溯率下降，B4 的误保存率上升，B5 的主链 p95 上升。

## 9. 统计和判定规则

- 主要指标预先登记：当前画像精确率、确定性日期 exact match、串槽率、日期漂移率、对话 p95、队列等待 p95。
- 同一用户内的回合不是独立样本，可靠性统计以用户为 bootstrap 单位；
- A/B 使用配对比较；分类结果使用 McNemar 检验，延迟使用 Wilcoxon signed-rank 或 bootstrap；
- 报告均值、中位数、p95、95% 置信区间和样本量；
- 不因某项指标失败而只报告通过指标；所有失败样本必须附带可复现的 `sample_id`。

### 通过门槛

实验系统 B 只有同时满足以下条件才允许默认开启：

1. 当前画像精确率 >= 98%；
2. 串槽率 = 0；
3. 确定性日期 exact match >= 98%；
4. 日期漂移率 = 0；
5. 重放一致率 = 100%；
6. 敏感信息拦截率 = 100%；
7. 对话总响应 p95 <= A 的 110%；
8. 正常负载队列等待 p95 <= 5 分钟；
9. 真实模型影子运行中，人工盲审错误率 <= 3%。

任一硬门槛不满足，只能保持 `proposal` 或 `legacy` 模式，不得默认 `commit`。

## 10. 输出物

每次实验必须输出：

- `run-config.json`：模型、温度、时区、版本、数据库 schema 版本；
- `metrics.json`：所有指标及置信区间；
- `failures.jsonl`：失败样本、输入、期望、实际和错误类型；
- `profile-snapshots/`：测试用户的画像快照和替代链；
- `report.md`：结论、门槛判断和下一步；
- 不包含真实个人信息、密钥、原始图片或未脱敏对话。
