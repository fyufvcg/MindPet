# MINDPET 对话、深度思考与行动记录设计方案

日期：2026-10-01  
交付范围：设计与实施方案，本轮不修改业务代码或界面。

## 1. 目标与确定的方向

本次调整围绕主聊天页：让用户先读清回答，再看懂当前正在执行什么，并能在对话结束后回看完整过程。

视觉采用接近 Codex 的轻量信息层级和紧凑过程反馈，沿用 MINDPET 的冷灰浅色、深海军蓝深色、克制蓝色强调及温和圆角。侧栏、桌宠、记忆模块和全局品牌体系不在本轮改造范围。

已确定的内容规则：**完整显示模型返回的思考内容，仅优化排版。** 不将其改写为摘要，不删减内容，不根据文本臆造阶段标题或思考步骤。行动记录来自真实执行事件。

## 2. 现有实现的问题

根据当前代码检查：

- 深度思考使用 `details` 和 `white-space: pre-wrap` 直接展示整段文本，缺少适合长内容的段落、列表、代码和标题层级。
- 深度思考、工具过程、正文分别渲染，工具过程位于回答正文之前，阅读顺序与“正文下方观察任务进展”的需求不一致。
- 展开的工具过程在运行时缺少常驻总控栏；收起状态固定显示成功图标，容易把仍在执行的任务表现成已完成。
- `isThinking` 同时承担整轮运行与推理阶段的含义，模型已经生成回答或开始调用工具时，标签仍可能显示“正在深度思考”。
- 步骤更新会强制把内部滚动区域滚到底，用户回看旧步骤时容易被拉走；耗时存在从步骤 ID 反推的逻辑。
- 已有前端工具事件监听和存储基础，但当前 Java 主对话链路主要记录工具调用日志，没有完整贯通所有工具的开始、进度、成功与失败事件。

本方案既调整呈现方式，也补齐真实过程数据。

## 3. 对话的整体布局

每条助手回复采用一个稳定的纵向结构：

1. 现有头像、名称和时间，降低元信息的视觉重量。
2. 流式回答正文，作为第一阅读区域。
3. 已生成文件、音频等交付物；等待用户操作时的提问或配置卡片。
4. 统一过程区，固定在本条回复正文下方，内部容纳“深度思考”和“行动记录”。
5. 现有复制、导出等消息操作。

尚未生成正文时，过程区直接出现在助手名称下方。正文出现后自然位于过程区上方；不制造大面积占位卡片。

普通文字正文建议使用 760–800px 的阅读宽度上限，随聊天列居中。窄窗口左右留白 12–16px，宽窗口约 24px。表格、代码和附件在需要时使用横向滚动，不能把整个窗口撑宽。

助手正文保持开放、平整的版式；用户消息保留现有浅底圆角气泡。统一正文、交付物和过程区的左侧起点。

### 运行时示意

以下内容是交互示意，不代表实际执行结果。

```text
MindPet                                      14:32

我先检查现有文件，再生成你需要的文档。
……正文继续流式生成……

◌ 任务进行中 · 正在创建 report.docx · 18秒     收起⌃

  深度思考                                    收起⌃
  │ 模型返回的完整思考内容，按原有段落排版。
  │ 原有列表、标题和代码使用一致的阅读样式。

  行动记录
  ✓ 读取文件  requirements.md       read_file      1.2秒
  ✓ 检查目录  output/               list_dir       0.4秒
  ◌ 创建文件  report.docx           generate_file  进行中
    正在写入正文，工具返回的进度在此持续更新。
```

### 用户主动收起时

```text
◌ 正在创建 report.docx · 已完成2步 · 18秒       展开⌄
```

收起只隐藏过程内容，任务照常运行，当前动作和耗时继续更新。

### 整轮结束后

```text
这是生成好的文档，已按你的要求整理。
[report.docx]

› 已完成 · 3项操作 · 26秒 · 含深度思考
```

结束态只保留一行小字和展开箭头，不保留整块卡片背景。点击该行可以重新查看全部思考内容和行动记录。

## 4. 深度思考的内容与排版

### 内容保持完整

- 保存模型返回的完整 `reasoningText`；渲染与原始文本分离。
- 尊重原始段落和换行。原文没有标题时不补标题，没有列表时不强行转换成列表。
- 原文包含 Markdown 时支持段落、轻量标题、列表、引用、行内代码和代码块。关闭原始 HTML 执行，链接沿用应用已有的安全打开方式。
- 不从思考文字中猜测“读取了文件”或“调用了工具”；这类事实只由行动事件确认。
- 首轮开启深度思考时，过程区与思考子区默认展开。用户手动收起后，后续文本增量不重新展开。
- 原文较长时提供“复制思考内容”，复制完整原文，不复制经过排版的摘要。

### 字体与阅读节奏

| 层级 | 建议规格 | 作用 |
| --- | --- | --- |
| 回答正文 | 14px，行高约1.7，常规字重 | 首要阅读内容 |
| 思考原文 | 13px，行高约1.7，次级文字色 | 长内容清晰阅读 |
| 思考内标题 | 13px，字重600，上方留12px | 尊重原有标题，保持低调 |
| 行动描述 | 12–13px，行高约1.55 | 快速理解每一步 |
| 工具名、路径 | 12px，现有等宽字体 | 保留技术识别信息 |
| 结束态单行 | 12px，次级文字色 | 提供轻量回看入口 |

沿用当前中文系统字体栈。正文段间距约10–12px，思考段间距8–10px，列表项间距4–6px。避免每段加框、加粗或使用彩色标题。

思考区域用一条细分隔线和约12px缩进体现层级。展开的原文区域高度建议不超过320px或窗口高度的35%，超出后在该区域滚动；用户向上阅读时暂停跟随，并提供“回到最新”。窄窗口仍维持可读字号，通过换行和缩进调整布局。

### 状态文案

| 实际阶段 | 展示文案 |
| --- | --- |
| 已开启，尚未收到推理内容 | 等待模型返回思考内容… |
| 正在收到推理增量 | 正在深度思考 |
| 推理阶段已结束，整轮仍运行 | 深度思考已结束 |
| 整轮正常结束，存在原文 | 深度思考 |
| 服务未返回推理内容 | 本次未返回可显示的思考内容 |
| 当前模型能力不支持 | 当前模型不支持显示思考内容 |

前两种等待状态不伪造填充文字。是否显示“不支持”基于能力信息或明确服务响应，不能仅凭模型名推断。若后端无法准确界定推理结束，使用中性的“深度思考”标题，避免把整轮运行当作持续推理。

## 5. 行动记录的显示规则

### 每次调用是一条稳定记录

工具启动时立刻出现，进度和结果更新同一条记录，不把一次调用拆成重复的“调用”和“返回”两行。顺序按真实开始事件排列；工具结果不改变行位置。

一条记录包含：状态图标、动作和对象、真实工具名称、耗时，以及可展开详情。

| 行为 | 启动时 | 成功后 |
| --- | --- | --- |
| 读取文件 | 正在读取 requirements.md | 已读取 requirements.md |
| 创建文件 | 正在创建 report.docx | 已创建 report.docx |
| 修改文件 | 正在修改 config.json | 已修改 config.json |
| 搜索内容 | 正在搜索相关资料 | 已搜索相关资料 |
| 运行命令 | 正在运行 npm run build | 命令执行完成 |
| 操作应用 | 正在切换窗口／输入文本 | 窗口已切换／文本已输入 |

常见工具使用中文动作映射，并在行尾保留真实工具名。未知 MCP 工具直接显示“正在调用 工具名”，保留服务来源，不猜测具体行为。长路径在概览行省略中间部分，完整路径可在详情中查看和复制。

进度文本、标准输出、返回值和错误说明放在该行下面的详情区，默认只显示当前运行步骤的短进度。参数与完整输出可单独展开，不能把大段 JSON 自动铺满对话。较大输出允许分段加载或查看完整日志，但不能静默删除步骤。统计中的“一项操作”指一次真实工具调用，进度帧和返回帧不重复计数。

除工具外，可记录已明确埋点的准备上下文、压缩上下文、生成回答等阶段，但不计入工具操作数量。内部工具只有确实执行并有事件时才显示；模型自述计划不能替代执行记录。

### 展开与收起

| 状态 | 过程区行为 |
| --- | --- |
| 新回复开始运行 | 默认展开，显示任务状态；尚无工具时显示当前阶段 |
| 用户在运行中收起 | 保持收起，单行显示当前动作；新事件不抢回展开状态 |
| 用户再次展开 | 显示现有完整过程，继续接收更新 |
| 某个工具完成 | 更新该步骤，不收起整个过程区 |
| 等待用户回答或配置 | 维持等待态，整轮仍运行；必要操作卡片始终可见 |
| 整轮完成 | 自动收起一次，停止运行标记，保留单行摘要 |
| 完成后再次展开 | 保持用户选择，历史数据更新不触发二次收起 |
| 生成失败或用户停止 | 结束运行并收起，单行明确显示“未完成”或“已停止” |
| 切换会话后回来 | 恢复该轮运行期间的折叠选择；结束的历史回复默认收起 |

运行中的总控栏始终存在，用户无须等待任务结束才可以收起。整轮结束以执行器的终态事件为准，不以第一个工具返回、出现正文或收到思考结束事件为准。

工具失败后重试必须保留失败记录和新的尝试。若已恢复并最终成功，可显示“已完成 · 含1次重试”；仍有未解决的失败时显示“部分完成”或“未完成”。结束后的失败摘要需可见，必要的解释和下一步操作保留在过程区之外。

### 滚动与动效

- 用户位于聊天底部时跟随新增内容；向上阅读后停止自动滚动，提供“回到最新”。
- 思考和行动详情内的滚动同样尊重用户位置，不在每次事件后强制滚到底。
- 折叠时保留正文的屏幕位置，避免因删除大块高度导致视口跳走。
- 仅当前执行状态使用小型旋转图标；支持减少动态效果。取消跳动圆点、发光连线和多处同时旋转的反馈。
- 展开、收起使用约150–180ms的轻量过渡，不逐帧平滑滚动。
- 所有折叠入口使用可聚焦按钮、明确的展开状态和键盘操作；折叠后焦点回到入口。辅助技术只播报重要阶段，不逐字播报全部输出。

## 6. 配色和组件形态

直接使用当前主题变量，例如 `--bg-content`、`--bg-card`、`--text-primary`、`--text-secondary`、`--text-muted`、`--border-card`、`--color-action-primary` 与语义状态变量。

| 角色 | 浅色主题 | 深色主题 |
| --- | --- | --- |
| 主体背景 | 当前冷灰／纸白底色 | 当前深海军蓝底色 |
| 过程文字 | 当前次级灰蓝文字 | 当前浅灰蓝文字 |
| 操作与运行强调 | #3976f6 对应的主题变量 | #74aaf4 对应的主题变量 |
| 分隔与悬停 | 现有细边线、低强度底色 | 现有细边线、低强度底色 |
| 成功、等待、失败 | 当前语义色变量，确保文字对比度 | 当前语义色变量，确保文字对比度 |

展开态采用平面信息分区，必要时使用6–8px圆角的极浅背景；结束态单行透明。状态色集中在小图标或关键文字，不铺满整行。普通成功步骤可以使用中性勾选，失败或等待状态再强化颜色。正文维持高对比，过程文字不能依靠低透明度牺牲可读性。

## 7. 数据与事件方案

### 贯通实际执行链路

建议沿用 Java NDJSON → Electron 主进程 → preload IPC → React 消息状态的现有架构。工具调用统一在执行入口产生事件，覆盖内置工具和 MCP 回调；由工具内部补充有实际意义的进度或子操作。

事件类型建议包含：

- `run_started`、`run_phase`：本轮启动及当前阶段。
- `reasoning_delta`、`reasoning_status`：保留现有思考增量，补齐准确的阶段状态。
- `tool_started`、`tool_progress`、`tool_finished`：一次调用的生命周期，结束状态包含成功、失败和取消。
- `run_waiting`、`run_resumed`：需要用户输入等等待阶段。
- `run_finished`：整轮完成、部分完成、失败或停止。

每个事件至少带有 `sessionId`、`messageId`、`runId`、`eventId`、`sequence`、`timestamp`；工具事件增加唯一 `callId`，必要时有 `parentCallId`。保留工具名、服务来源、动作类型、对象、开始与结束时间、进度文本以及结构化状态。

同名工具并行执行或连续重试必须依靠 `callId` 配对。`sequence` 用于保持真实顺序，`eventId` 用于去重；不能靠工具名、随机前端 ID 或事件到达时间配对。

后端输出器统一串行写入，保证并行工具不会把 NDJSON 行写乱。执行回调须显式传递本轮上下文，不能只依赖跨线程不可靠的 ThreadLocal。工具失败优先依据结构化返回或执行异常，不能把结果字符串含有“错误”直接等同于失败。

不同工具能力下，显示它们实际报告的步骤：单个复合工具未提供内部阶段时，只展示该工具调用；不能虚构“检查、写入、保存”三步。终端执行时先显示命令，只有得到可靠的文件操作事件才展示创建或读取文件。

### 前端状态和落盘

- 保留现有正文和思考字段，新增本轮状态、当前阶段、准确起止时间以及结构化行动记录。
- 将运行状态、推理状态、单个工具状态、用户折叠选择分别管理；兼容现有依赖 `isThinking` 的界面，但不继续用它推断所有阶段。
- 同一消息内统一归并正文、思考和工具事件，最终完成前先提交全部缓冲增量，再落盘和触发收起，避免遗漏最后一段思考或工具结果。
- 主进程持有本轮状态和耗时基准，窗口切换或重建后可恢复；历史缺少时间时不显示虚构耗时。
- 记录开始即写入，进度按现有批处理机制更新，终态立即保存。完成后回看原文和行动记录时无需重新请求模型。
- 重启后无法恢复的运行记录明确标为“已中断”，未确认完成的文件操作标为“状态未知”，不能直接改成成功。
- 旧 `toolSteps` 通过兼容适配转成新的行视图；配对不确定时保留原记录并标注未知，避免丢失历史数据。
- 参数与输出展示时处理密钥等敏感字段，错误详情使用受控文本渲染；思考与行动记录不无条件重新注入模型上下文。

## 8. 实施拆分

1. **先贯通事件。** 为 Java 工具回调及本地执行入口补齐生命周期事件，扩展 NDJSON 与 IPC 透传，确认读取、创建、修改、命令、MCP 均能真实上报。
2. **建立统一状态归并。** 补充 `runId`、`callId`、状态与时间字段，处理并行、重试、停止、终态缓冲提交和历史落盘。
3. **替换对话呈现。** 从大组件中拆出 `ReasoningContent`、`ActivityRow`、`MessageProcessPanel`，正文排在过程区之前，统一排版和折叠交互。
4. **进行主题与场景验收。** 检查深浅主题、宽窄窗口、长思考、多步骤、回看、失败及历史记录。

主要涉及的现有文件：

- `MindPet/src/renderer/src/components/ChatMessageItem.tsx`：调整层级，替换思考与过程展示。
- `MindPet/src/renderer/src/pages/ChatPage.tsx`：阅读宽度、跟随滚动和输入区状态文案。
- `MindPet/src/renderer/src/hooks/useChatStreamEvents.ts`、`useChatToolEvents.ts`、`useChatReplyRuntime.ts`：事件归并、终态提交与折叠触发。
- `MindPet/src/renderer/src/assets/main.css`：对话、思考和行动记录的主题化样式。
- `MindPet/src/main/backend-api.ts`、`index.ts`、`src/preload/index.ts` 及类型定义：事件完整透传。
- `MindPet/src/main/file-store.ts` 及现有消息持久化入口：保存与恢复本轮状态和记录。
- `MindPet-java/src/main/java/service/AiService.java`、`controller/DesktopController.java`、工具上下文和执行入口：真实生命周期事件、线程上下文及串行输出。

实际实施时先确认现有消息存储结构，再决定是否需要数据迁移；不在方案阶段假定存储已经支持全部新字段。

## 9. 验收标准

- 深度思考原文完整保留，段落、列表与代码可读，复制得到完整原文。
- 正文处于主要阅读位置，行动记录始终在本条流式正文下方。
- 真实工具启动后及时出现记录，能看到工具名、对象和状态；进度更新不重复增加操作数。
- 用户运行中可以随时收起和展开，增量事件不覆盖用户选择。
- 工具结束不使整轮提前完成；整轮结束自动收起一次，随后可以长期展开回看。
- 运行态不会使用成功图标；停止、失败、部分完成与等待用户输入有明确区别。
- 多次同名调用、并行与重试配对准确，失败记录保留，不串到其他会话或消息。
- 用户回看时没有强制滚动，完成收起不造成明显视口跳跃。
- 文件交付物和必要操作入口不随过程区一起隐藏。
- 深浅主题和窄窗口均可读，键盘可操作，状态颜色具有足够对比度。
- 重开应用后能够回看已经保存的原文和步骤，无法恢复的任务不显示虚假完成状态。
