# MindPet Retrieval Benchmark 设计说明

## 1. 目标与边界

本基准用于比较 MindPet 长期记忆检索的四种模式：`keyword_only`、`vector_only`、`rrf` 和 `mindpet_full`。第一版规模固定为 120 条记忆与 40 条查询，重点是让端到端评测流水线拥有一组规模可控、答案可人工复核、同时覆盖典型困难情形的数据。

本阶段只生成静态 JSONL 数据并校验结构，不写入 PostgreSQL/Redis，不生成 embedding，不调用 Java API，不运行检索、指标计算或绘图。数据本身不代表任何实验结论。

## 2. 文件与可重复生成

- `datasets/retrieval/memories.jsonl`：120 条候选记忆。
- `datasets/retrieval/queries.jsonl`：40 条查询及人工标注的相关记忆 ID。
- `scripts/generate_small_dataset.py`：纯标准库、无随机数的确定性生成器。
- `scripts/validate_retrieval_dataset.py`：独立读取最终 JSONL 并验证结构、分布和引用完整性。

生成器默认拒绝覆盖非空数据，只有显式传入 `--force` 才会覆盖。相同版本的生成器总是按 `m001..m120`、`q001..q040` 的稳定顺序生成相同内容，方便 Git 审阅和复现实验。

## 3. Memory 设计

### 3.1 类别分布

120 条记忆分为 12 类，每类严格 10 条：

| category | 数量 | 主题示例 |
|---|---:|---|
| sport | 10 | 羽毛球、游泳、跑步、运动限制 |
| food | 10 | 喜好、忌口、过敏、日常饮食 |
| study | 10 | 学习节奏、地点、课程和薄弱项 |
| work | 10 | 深度工作、任务管理、沟通方式 |
| software_tools | 10 | IDE、数据库、终端和接口工具 |
| schedule_time | 10 | 起床、睡眠、提醒、周期性安排 |
| relationships | 10 | 家人、朋友、同事和导师 |
| places | 10 | 学习、运动、旅行和采购地点 |
| devices_environment | 10 | 电脑、外设、温度和备份设备 |
| projects | 10 | MindPet 架构、当前目标和旧项目 |
| personal_facts | 10 | 城市、生日、通勤和个人特征 |
| entertainment_hobbies | 10 | 播客、电影、摄影、阅读和绘画 |

### 3.2 字段设计

每条记忆包含：

- `memory_id`：稳定 ID，范围 `m001..m120`。
- `user_id`：统一为隔离的评测用户 `eval_test_user`。
- `content`：自然中文陈述，既包含可精确匹配的实体，也包含可语义改写的事实。
- `importance`：范围 0 到 1；安全、身份、当前项目目标等值更高，弱偏好和旧事实更低。
- `confidence`：范围 0 到 1；明确事实接近 1，带“偶尔”“可能”等不确定表达略低。
- `layer`：只取 1、2、3，用于覆盖不同记忆层级。
- `emotion`：`positive`、`neutral`、`negative`。
- `created_at_offset_hours`：相对导入基准时间向过去偏移的小时数，全部非负，不制造未来时间。
- `category`：上述 12 类之一。
- `tags`：至少两个用于人工审阅的主题标签，不作为 ground truth 的替代品。

### 3.3 时间和重要性对照

数据包含明确的新旧状态对：

- `m101` 现在常住南京，`m102` 以前住过苏州。
- `m111` 现在通勤听科技和历史播客，`m118` 以前常听流行音乐、现在很少听。
- `m096` 是当前最重要的检索评测目标，`m097` 是偶尔维护的旧项目。
- `m114` 是最近主要坚持的街头摄影，`m119` 是如今只偶尔进行的速写。

这些对照用于检测时间、importance、confidence、layer 等完整 rerank 因素是否能帮助当前事实排在旧事实之前；它们不预设该提升一定发生。

## 4. Query 设计

### 4.1 类型分布

| query_type | 数量 | 主要观察目标 |
|---|---:|---|
| exact_keyword | 8 | 明确实体或原词是否被关键词通道命中 |
| semantic_paraphrase | 10 | 查询不复述关键答案词时的语义召回 |
| hybrid | 8 | 词面约束与语义槽位共同存在时的表现 |
| multi_candidate | 6 | 近邻候选区分或多答案完整召回 |
| temporal_importance | 4 | 新旧事实、重要性与完整 rerank 的影响 |
| no_answer | 4 | 没有相关记忆时是否避免无依据返回 |

难度标签分为 `easy`、`medium`、`hard`，只用于切片分析，不参与检索打分。

### 4.2 Ground truth 标注原则

`relevant_memory_ids` 由查询能否被记忆内容直接支持来确定：

1. 答案必须能从目标记忆内容中得出，不能依赖常识补全。
2. 同义改写不改变相关性，例如“最爱做什么运动”对应“最喜欢的运动是羽毛球”。
3. 当查询明确需要多个槽位时，所有直接回答槽位的记忆都标为相关，例如跑步地点和羽毛球地点分别对应 `m073`、`m074`。
4. 主题接近但不能回答问题的候选不标相关。
5. 带“现在”“目前”“主要”等时间限定词的查询，只把当前状态标为相关，历史状态作为困难负例。
6. `no_answer` 查询的相关 ID 必须为空，并且其答案主题在候选记忆中不存在。

第一版采用二元相关性，不区分“完全相关”和“部分相关”。因此 nDCG 使用二元 gain；以后若扩展分级相关性，需要单独版本化标注格式。

### 4.3 多答案查询

共有 4 条查询包含两个相关记忆：

- `q029`：跑步地点与羽毛球地点。
- `q030`：桌面键盘与鼠标。
- `q031`：长期记忆与短期记忆的存储技术。
- `q032`：街头摄影与偶尔速写两项动手创作爱好。

另外两条 `multi_candidate` 查询只有一个正确答案，但放置了语义邻近的困难负例，侧重测试候选区分，而不是多答案覆盖。

## 5. Hard Negative 设计

困难负例与目标记忆共享人物、工具、场景或主题，但不满足查询的关键约束：

- `q027` 询问紧急需求的范围确认方式，`m035` 是答案；`m036` 同样描述沟通方式，但没有“确认范围和验收标准”。
- `q028` 询问用于数据探索和快速画图的 Python 工具，`m044` 是答案；`m043` 虽也是 Python IDE，却只用于维护旧工程。
- `q033` 当前居住地为南京；苏州仅是过去居住地。
- `q034` 当前通勤内容为科技和历史播客；流行音乐是已经降低频率的旧习惯。
- `q035` 当前核心项目目标是四种检索模式评测；旧天气机器人不是当前目标。
- `q036` 当前主要周末创作活动是街头摄影；速写现在只是偶尔进行。

这些设计可暴露“只看主题相似度、不理解条件与时间限定”的排序错误。

## 6. 四种模式的预期区分能力

以下是数据设计希望观察的现象，不是实验结果：

- `keyword_only`：应在产品名、人名、地名和原词查询上具备优势；对于完全改写、未包含答案实体的查询可能较弱。
- `vector_only`：应更适合语义改写；但在近邻工具、人物或时间状态之间可能发生混淆。
- `rrf`：应能合并两个通道的互补候选，使同时得到语义和关键词支持的记忆上升；纯 RRF 不应使用时间、importance、confidence 等额外因素。
- `mindpet_full`：在 RRF 基础上使用当前 Java 源码真实存在的 rerank 因素，重点观察时间与重要性对照组是否受益。

模式间必须使用同一批数据库数据、同一查询、同一 TopK 和同一 embedding 方案，才能进行公平比较。

## 7. No-answer 设计与评价注意事项

4 条无答案查询分别询问乐器、宠物姓名、汽车品牌和滑雪场。这些主题在 120 条记忆中均没有对应事实，`relevant_memory_ids` 严格为空。

传统 Recall、MRR、nDCG 对空相关集合通常定义为 0 或跳过，无法单独反映系统是否正确拒绝。后续正式评测除统一约定空集合指标处理方式外，建议增加：

- `no_answer_hit_rate`：TopK 中没有返回不相关记忆的比例（前提是系统支持空结果/阈值）。
- 阈值下的误召回率。
- 有答案与无答案查询分开报告，避免汇总值掩盖行为。

当前检索 API 如果固定返回 TopK 且没有拒答阈值，则 no-answer 数据主要用于观察错误候选及分数分布，而不能直接证明“拒答成功”。

## 8. 校验规则

校验器会失败退出，除非同时满足：

- JSONL 是 UTF-8、逐行合法 JSON 对象且没有空行。
- 恰好 120 条记忆、40 条查询。
- ID 唯一、连续，并保持稳定顺序。
- 12 个记忆类别各 10 条。
- 六类查询数量严格为 8、10、8、6、4、4。
- 所有字段存在，数值范围、layer、emotion、difficulty、user ID 和时间偏移合法。
- 所有关联记忆 ID 存在且同一查询内不重复。
- `no_answer` 的相关 ID 为空，其他查询至少有一个相关 ID。
- 至少 4 条查询包含多个相关答案。
- 无答案主题关键字不出现在候选记忆正文。

## 9. 已知限制

1. 数据是人工构造的单用户中文小样本，不能代表真实用户分布。
2. 只标注二元相关性，没有多级 gain 或标注者一致性统计。
3. 同一事实大多只出现一次，尚未覆盖大量重复、冲突、跨语言和长文本记忆。
4. `created_at_offset_hours` 是相对时间，导入器必须以同一个基准时刻换算，不能直接当成绝对时间。
5. 当前关键词通道若先按 importance 截断候选，再做文本排序，低 importance 的相关记忆可能无法进入候选池；这是待实测的真实实现限制，不应在数据集里绕开。
6. 无答案测试需要检索阈值或空结果能力配合，单靠 TopK 排名指标不足以评价。
7. 本报告只描述设计，不包含任何伪造的检索分数或指标。

## 10. 后续使用建议

1. 先运行校验器并记录数据文件的 Git 版本或哈希。
2. 将 120 条记忆只导入隔离数据库 `mindpet_eval`，使用 `eval_test_user`，严禁写入正式库 `mindpet`。
3. 以统一基准时间把 `created_at_offset_hours` 换算成 `created_at`，并使用同一 embedding 模型生成向量。
4. 针对四种 RetrievalMode 运行完全相同的 40 条查询，保存逐查询排名、各 lane 调试字段和最终分数。
5. 先按全部查询计算 Precision@K、Recall@K、MRR、nDCG@K，再按 `query_type` 和 `difficulty` 切片分析。
6. 单独审阅 no-answer、时间状态对和多答案查询，不仅查看汇总均值。
7. 扩容前先人工审查第一轮错误案例，再决定增加真实脱敏数据、冲突记忆、多轮查询或分级相关性。
